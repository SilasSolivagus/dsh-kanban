# P1.2 — review gate live acceptance runbook

**Date:** 2026-10-23
**Scope:** Task 7 live acceptance for the builder → reviewer gate.
**Status:** Runbook ready. The live result is recorded by the controller after execution; this file deliberately contains no live card ids or verdicts.

## Purpose

Prove on a live DSH Kanban instance that a builder Done candidate cannot reach Done without a reviewer pass, and that a reviewer reject leaves the card in **Needs you**. The fake end-to-end coverage lives in `src/host/__tests__/supervisor-cycle.test.js`.

## Preconditions

- The plugin is enabled and the supervisor timer is running (default interval 5s).
- The live worker config has two roles, `builder` and `reviewer`, each with a real absolute `cwd`, a positive `maxConcurrent`, a positive `timeoutSeconds`, and a valid `agentPreset` (`standard` unless the instance says otherwise).
- Both `docs/agents/builder.md` and `docs/agents/reviewer.md` are readable through the worker config's prompt resolution.
- The builder workspace can complete a small real task and run at least one command it can cite as evidence.
- The reviewer workspace is separate from the builder workspace.
- No manual status edits are made during the run.
- Tokens, cookies and internal addresses never appear in cards, comments or prompts.

## Path A — reviewer pass

1. Create one card in the Web UI with a concrete, checkable acceptance and assign it to `builder`.
2. Wait for the supervisor cycle. Do not edit status by hand.
3. Confirm the card moves `backlog` (or `todo`) → `in_progress` while the builder works.
4. Confirm the builder returns `outcome: done` with at least one evidence entry, and the evidence is commented on the card under author `builder`.
5. Confirm the card moves to `reviewing`, not `done`; the card stays in the Running column while reviewing.
6. Wait one more supervisor cycle. The handoff is intentionally deferred, so the reviewer picks up the card on the next tick.
7. Confirm the reviewer session receives the card plus the builder's evidence comments, and returns `verdict: pass`.
8. Confirm the card ends at `done`, the pass comment is authored by `reviewer`, and no human wrote the Done status.

Expected sequence:

```text
backlog/todo -> in_progress -> reviewing -> done
```

## Path B — reviewer reject

1. Create a second card whose acceptance the builder cannot satisfy, or whose builder evidence is intentionally missing the required check. Assign it to `builder`.
2. Let the builder submit its Done candidate as in Path A.
3. Confirm the card reaches `reviewing`.
4. Wait one more supervisor cycle so the reviewer evaluates it.
5. Confirm the reviewer returns `verdict: reject`, writes the missing acceptance point as the summary, and the card stays `reviewing` with `blockedReason` set to that summary.
6. Confirm the card appears in **Needs you**, and no Done status was written.
7. Confirm a later supervisor cycle does not re-prompt the rejected card while `blockedReason` is present.

Expected state:

```text
reviewing + blockedReason -> Needs you
```

## Acceptance checklist

- [ ] A `reviewer` role starts and receives work; a `builder`-only card cannot reach Done through the builder path.
- [ ] Builder Done candidate lands in `reviewing` on the first cycle.
- [ ] Reviewer pass lands in `done` on a later cycle, with reviewer-authored verdict comment.
- [ ] Reviewer reject stays in `reviewing`, sets `blockedReason`, and shows in **Needs you**.
- [ ] `in_review` is untouched by the reviewer gate; it remains the human attention state.
- [ ] Rejected cards are not re-prompted on the next cycle.
- [ ] No manual status edits and no duplicate prompts during the run.
- [ ] Card ids, card titles, observed transitions, comment authors and verdict summaries are captured for the result record.

## Recording the result

After execution, the controller appends a `## Live result` section to this file with:

- date and DSH/plugin version
- supervisor interval and worker ids used
- Path A card id, title, observed transitions and reviewer comment summary
- Path B card id, title, observed transitions, `blockedReason` and reviewer comment summary
- any deviations or fixes found during the run

Until that section exists, treat the live acceptance as not executed. The fake end-to-end tests prove the code path; they do not replace the live card.

## Rollback and failure handling

- If the builder card goes straight to Done, stop the run: either the reviewer is missing from the live config or the handoff branch is not active. Check `workerByRole(workers, 'reviewer')` and the supervisor log before retrying.
- If the reviewer cannot be prompted, check its `cwd`, role prompt path and persistent session state; do not edit the card status to force progress.
- If a rejected card is re-prompted, stop the run and record the card id and the supervisor log line; that is a gate defect.
- To stop the supervisor, disable the plugin or remove the live worker config; no board data or live config is changed by this runbook.
